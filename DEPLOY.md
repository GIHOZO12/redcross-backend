# Deploying to Render

The app is already configured for Render. Database is on Supabase, uploads are
on Cloudflare R2, and static files are served by WhiteNoise from the app
process. Nothing needs to change in the code.

Files that drive the deploy:

| File | Purpose |
| --- | --- |
| `render.yaml` | service definition: region, plan, commands, env vars |
| `build.sh` | runs on every deploy: install, `collectstatic`, `migrate` |
| `.env` | **local only** — never committed; Render gets its own values |

---

## 1. Push the code to GitHub

Render deploys from a Git repository, so the code has to be on GitHub first.

```bash
git add -A
git commit -m "Add Swagger docs, Supabase/R2 config, Render deployment"
```

`.gitignore` already excludes `.env`, `db.sqlite3` and `media/` — verify before
pushing, because those hold real user data:

```bash
git check-ignore .env db.sqlite3 media       # should print all three
git ls-files | grep -E "\.env$|db.sqlite3"   # should print nothing
```

Create an **empty** repository on GitHub (no README, no .gitignore), then:

```bash
git remote add origin https://github.com/<you>/<repo>.git
git branch -M main
git push -u origin main
```

Make the repository **private** if you can. It contains no secrets, but it does
describe your whole API surface.

## 2. Create the service on Render

1. Sign up at [render.com](https://render.com) with your GitHub account.
2. **New → Blueprint**, pick the repository.
3. Render reads `render.yaml` and proposes a web service named
   `redcross-backend` in Frankfurt on the free plan.
4. It will prompt for every variable marked `sync: false`. Fill them in from
   your local `.env`:

| Variable | Where to get it |
| --- | --- |
| `DATABASE_URL` | your `.env` — the Supabase **session pooler** string, port 5432 |
| `R2_BUCKET_NAME` | `redcross` |
| `R2_ENDPOINT_URL` | `https://<account-id>.r2.cloudflarestorage.com` |
| `R2_ACCESS_KEY_ID` | your `.env` |
| `R2_SECRET_ACCESS_KEY` | your `.env` |
| `R2_CUSTOM_DOMAIN` | the `pub-....r2.dev` host, **no `https://`** |
| `EMAIL_HOST_USER` | your Gmail address |
| `EMAIL_HOST_PASSWORD` | the Gmail app password |
| `DEFAULT_FROM_EMAIL` | your Gmail address |

`DJANGO_SECRET_KEY` is generated by Render, and `DJANGO_DEBUG` is already
`False`. You do **not** set `DJANGO_ALLOWED_HOSTS` — settings.py picks up
Render's `RENDER_EXTERNAL_HOSTNAME` automatically and adds it to both
`ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS`.

5. **Apply**. The first build takes a few minutes.

---

## 3. Check it came up

Once the deploy is green, with `<app>` as your Render URL:

```bash
curl https://<app>.onrender.com/api/healthz/
# {"status":"ok","database":"ok"}
```

`database: ok` proves Render reached Supabase — the thing PythonAnywhere's free
tier could not do.

Then in a browser:

- `https://<app>.onrender.com/admin/` — should load **with CSS** (that is
  WhiteNoise working). Log in with an existing superuser account; the password
  hashes came across in the migration, so your old password still works.
- `https://<app>.onrender.com/api/docs/` — returns **403 unless you are logged
  in as staff**. That is deliberate. Log into `/admin/` first, then reload.

## 4. Keep it awake (optional, free)

Free Render services sleep after 15 minutes idle, and the next visitor waits
roughly a minute for the cold start.

Sign up at [UptimeRobot](https://uptimerobot.com) or
[cron-job.org](https://cron-job.org) and add an HTTP monitor:

```
URL:      https://<app>.onrender.com/api/healthz/
Interval: every 10 minutes
```

Two things fall out of this:

- 744 hours of continuous uptime per month fits inside Render's 750 free
  instance-hours, so this stays free.
- `/api/healthz/` runs a `SELECT 1`, which also stops your **Supabase** free
  project pausing after 7 days of inactivity.

## 5. Point the frontend at it

Once the frontend is deployed, update these on the Render service
(**Environment** tab) and let it redeploy:

```
DJANGO_CORS_ALLOWED_ORIGINS=https://your-frontend.com
DJANGO_CSRF_TRUSTED_ORIGINS=https://your-frontend.com
```

Comma-separated, no spaces, scheme included, no trailing slash. Leaving the
deployed frontend out of this list is the usual cause of CORS errors in
production.

## Troubleshooting

**Build fails on `pip install`** — check `requirements.txt` is still UTF-8. It
was originally UTF-16, which Linux `pip` cannot read; it has been converted,
but some Windows editors will convert it back if you edit and save it.

**`DisallowedHost` error** — `RENDER_EXTERNAL_HOSTNAME` was not picked up. Add
your Render hostname to `DJANGO_ALLOWED_HOSTS` manually.

**Database connection times out** — the `DATABASE_URL` is probably the direct
connection (`db.<ref>.supabase.co`), which is IPv6-only. It must be the session
pooler host on port 5432.

**`migrate` fails during build** — most likely the transaction pooler (port
6543) rather than session mode (5432).

**Admin loads without CSS** — `collectstatic` did not run; check the build log
and that `build.sh` is executable (`git update-index --chmod=+x build.sh`).

**Images 404 or show as broken** — `R2_CUSTOM_DOMAIN` has `https://` in it. It
must be the bare hostname.

**No shell on the free plan** — Render's Shell tab needs a paid instance. To
run a one-off management command, add it temporarily to the end of `build.sh`,
deploy, then remove it. You already have 3 superusers in the database, so you
should not need `createsuperuser`.

## Still outstanding before real users

- `/api/download_single_user_info/<id>/` serves a PDF containing a member's
  national ID and home address, with **no authentication**, keyed on a
  guessable integer.
- The newsletter send loops over subscribers synchronously inside the request
  and will exceed the gunicorn timeout once the list grows.
- Enable HSTS (`DJANGO_HSTS_SECONDS=31536000`) once HTTPS is confirmed working.
- Delete the two spare Cloudflare R2 API tokens.
